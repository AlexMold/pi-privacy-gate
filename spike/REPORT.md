Дата: 2026-10-26. Машина: Mac (Apple Silicon, Metal), llama-server из brew (v0.7.0-совместимый).

## Наблюдения и риски

- **Размер окна — критичен (найдено в M1):** модель теряет PII у хвоста длинного окна. Замер на повторяющемся тексте: детект надёжен при ≤~1400 токенов перед спамом, провалы с ~1600+; на вариативном тексте порог выше (~1200 слов ок, 1500 — мимо при окне 4096). Решение: **окно 1024 токенов без оверлапа** — любой спам не дальше 1023 токенов от начала окна. Цена: больше запросов (~0.35ms/токен + ~70ms/запрос).

- **private_date граничный дефект:** «1992-03-14» детектится как «992-03-14» (первая цифра потеряна) при score 1.000 — артефакт границы токена модели, не нашего порта. Лечится калибровкой порогов, не кодом.
- **Латентность на пути tool_result:** ~1.4s на полный чанк 4096 токенов. Вывод bash на 50KB ≈ 13K токенов ≈ 4 чанка ≈ 5-6s. Это честная цена сканирования «всех tool results»; смягчение — лимит размера в конфиге (M1) + кэш по hash содержимого.
- **Sensitivity-голова на коротких текстах даёт ~0.03** — conversation-level чувствительность бесполезна для tool results (это не «разговор»). В v1 опираемся на span-детекцию; sensitivity оставляем сырым в API, не используем в предикатах.

## SYSE.24:4.3 — сравнение arrangements

| Вопрос | A: TS-порт + llama-server | B: Python-sidecar (numpy+tokenizers) |
|--------|---------------------------|--------------------------------------|
| Результат | Детектор целиком в npm-пакете, единственный внешний процесс — llama-server | Плюс Python-процесс и venv |
| Кто что делает | Расширение: spawn llama-server; TS: токенизатор, головы, Viterbi | Python-сервис: всё, кроме llama-server |
| Производство/доступ | npm install — и всё | npm + python3 + pip venv (не гарантирован на машинах юзеров) |
| Интеграция | Один супервизируемый процесс | Два процесса, IPC, версионный дрейф |
| Основание для доверия | Byte-exact сверка токенизатора (этот спайк) + канонический пример | Та же корректность; numpy надёжен |
| После первого запуска | Обновления = npm + веса | Плюс дрейф venv/python |
| Способности | TS-BPE переиспользуем; новых требований к машине нет | Требует Python-окружение у юзера |
| Ресурсы | 1.2GB весов + 16MB бинарник + ~1.4s/чанк | То же + ~50MB Python-зависимостей |

## Решение

**GO по варианту A: полный TS-порт, без sidecar.** Основание: byte-exact токенизация доказана на живом сервере, канонический пример сошёлся, Python-зависимости юзеру не нужны — ключевое для дистрибуции комьюнити с разными локальными сетапами.

Остаточные условия: (1) калибровка порогов span-confidence в M1 с дефолтами; (2) sensitivity-голова в v1 не участвует в предикатах; (3) бюджет латентности честно задокументировать в README; (4) окно сканирования — 1024 токена (см. Наблюдения).
